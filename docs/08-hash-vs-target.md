# 8. H 与 T 的整数比较

## 挖矿判定的最后一步

算出 H 后，判定"是否挖到"只有一句话：

```
把 H 和 T 都看作 256 位无符号整数，判断 H ≤ T
```

就这么朴素。没有"哈希格式转换"、"有效解验证协议"之类的花样。

## 一个新手大坑：前导零 ≠ 比较规则

很多教程说"哈希前面 0 越多越好"。这只在"目标 T 的前导零比哈希多时"
碰巧等价，**不是共识规则**。反例：

```
T = 0x00000000FFFF0000...00
H = 0x0000000000008000...00   前导零 59 个，满足 H ≤ T ✓
H = 0x00000000FFFF0000...01   前导零 32 个，仅比 T 大 1，不满足 ✗
```

第二个哈希的前导零不少，但它在及格线上方 1，仍然不及格。
**比特币节点执行的是完整 256 位整数比较**，本项目也一样：

```python
from bitcoin_pow.target import compare

t = 0x00000000FFFF0000000000000000000000000000000000000000000000000000
# H == T：算满足（≤ 包含等于）
compare((t).to_bytes(32, "little"), t)          # True
# H == T + 1：只差 1 也判负
compare((t + 1).to_bytes(32, "little"), t)      # False
```

本仓库测试 `tests/test_target.py` 专门覆盖了 H = T−1 / H = T / H = T+1
三个边界，并用"高 16 位相同、末位差 1"的用例防止任何人写出
"只看前缀"的偷懒实现。

## 字节序：为什么代码里到处是反转？

SHA-256 吐出 32 字节：`b0 b1 b2 ... b31`（协议序）。
比特币把这串字节当作**小端**整数解释：

```
整数值 = b0×256⁰ + b1×256¹ + ... + b31×256³¹
```

也就是说 **b31 是最高位字节**。这正好等于"把字节倒过来按大端读"——
所以区块浏览器展示的哈希（大端）就是整数的常规写法：

```
展示序 = b31 b30 ... b0  →  int(展示序hex, 16) 就是那个 256 位整数
```

本项目统一约定：
- **比较**：`int.from_bytes(digest, "little") <= T`（完整 256 位）；
- **展示**：字节倒序后的 64 位十六进制（和区块浏览器一致）；
- **CUDA 内核**：逐字比较前先做 32 位字节反转（`bswap32`），
  语义与 CPU 完全一致，且经真实创世 Nonce 命中交叉验证。

## 完整流程串起来

```
80字节区块头 ──SHA256d──▶ 32字节 H ──小端解释──▶ 256位整数
                                              │
        0x1d00ffff ──解码──▶ 256位目标 T ─────┴──▶ H ≤ T ?
                                              │
                              是：宣布挖到 / 否：Nonce+1 继续
```
